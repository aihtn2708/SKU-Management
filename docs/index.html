SKU Management System

Every market reports sales against its own local product codes. This system maps each of those child SKUs to one canonical mother SKU, so a strawberry lollipop sold in Hanoi and one sold in Manila roll up to the same line in the consolidated P&L.

The problem

Three datasets, one canonical catalogue

The app asks for three files. Column names are detected by keyword, so most exports work as they are.

1 · Master Mother SKUs

The canonical registry. One row per global product, with a code and description; brand, pack type and weight are optional.

M1001 · Alpenliebe Strawberry Lollipop 24 Pouch

2 · Historical Mappings

Child → mother links already approved in past cycles. Exact codes are carried forward; their descriptions also act as a synonym list.

VN-24001 · AL Straw LLP 24px → M1001

3 · New Unmapped SKUs

The raw P&L extraction from each market: local code, local description, and optionally a country or market column.

VN-24015 · AL Strawberry Lollipop 24 Pouch new
The engine

History first, then semantic matching

Each new child SKU passes through up to three tiers. The confidence score decides whether a person needs to look at it.

Tier 1 · Exact history

If the child code already appears in the history file, its old mother is reused with confidence 1.0. No model is involved.

Tier 2 · Fuzzy via history

The description is embedded with all-MiniLM-L6-v2 and compared to every past child description. If the best past synonym beats the best mother, its mother is proposed.

Tier 3 · Fuzzy direct

Otherwise the closest canonical mother description wins. Scores above 0.85 are auto-confirmed, 0.45–0.85 wait in the Workbench, the rest go to the Unmapped queue.

Text normalisation

What the model actually compares

Local descriptions are full of shorthand. Before embedding, advanced_normalize() expands brand abbreviations, applies the country dictionary, and strips pack sizes so that “24px” and “45 bag” don't dominate the match. parse_specs() keeps those sizes separately for the reviewer.

Run it

Start the real app

The repo opens in GitHub Codespaces with the dev container, which installs requirements and starts Streamlit on port 8501. Locally it is two commands.

pip install -r requirements.txt
streamlit run app.py

What differs in this mock-up

The browser cannot load the MiniLM model, so similarity here is a character-trigram and token-overlap score that uses the same 0.45 and 0.85 thresholds. Normalisation, spec parsing, tier order, routing, conflict detection and the export join are ported directly from app.py. Nothing leaves your browser.
